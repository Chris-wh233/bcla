# gen-maker：从 BCLA 任务生成扁平构建项目

`gen-maker` 用于 BCLA 任务完成后的项目交付：读取工作区、终版文件和实际构建日志，将成功采用的构建方案整理成独立的 Dockerfile/Makefile 项目。它不生成知识库经验，不修改原任务，也不把探索过程或失败方案带入交付目录。

## 使用场景与输入

适合“把刚完成的 BCLA 任务整理成扁平项目”“根据这个 workspace 和构建日志生成一键构建目录”等请求。可以提供任务 ID、工作区与日志路径、输出目录和镜像命名；对话中已有的信息无需再次提供。

已安装此 skill 时，可以这样调用：

```text
@BCLA $bcla:gen-maker 生成扁平构建项目，输出到 /home/chris/proj/example。
```

显式任务 ID 优先；未指定时选择当前会话的任务，有多个时选择最近创建的任务，不会选择全局最新任务。选中任务必须为 `SUCCEEDED` 且成功证据完整，否则反馈缺口，不会自动转选旧任务。无法可靠确认会话归属时需要提供任务 ID。

默认输出到 `<BCLA_HOME>/exports/<任务ID>/`，也可以指定其它目录。已有目录中的用户修改和不同导出内容会保留。本技能随 BCLA 插件安装。

Skill 优先读取 BCLA 的只读任务、终版文件和执行记录；没有 BCLA 工具时，也能根据本地工作区和保存的日志工作。它会核对提交、文件摘要、成功命令和实际消费的产物，防止误用工作区中遗留的试验文件。若缺少关键终版文件、原生产物或镜像关系，会明确指出缺口，不会猜造文件或宣称完整交付。

## 扁平目录规则

单镜像项目的基本结构如下，按实际需要选择依赖：

```text
example/
  Dockerfile
  Makefile
  README.md
  entrypoint.sh.upstream
  entrypoint.patch
  entrypoint.sh
  config.conf
  native-library.so
```

`entrypoint.sh` 可以由 Makefile 从原始文件和补丁生成。普通上游源码仓库、构建缓存和任务日志不会整份复制进来；同名文件使用有意义的前缀区分，并相应调整 Dockerfile。容器内的安装路径、文件权限和运行行为保持一致。

## 依赖分类

依赖来源的优先级高于文件大小：

| 依赖情况 | 处理方式 |
| --- | --- |
| 无可用上游 LoongArch 版本，BCLA 单独原生构建，Dockerfile 在外部消费该产物 | 无论大小，都将实际成功使用的产物放进项目。保留必要的配套文件、权限和链接，记录来源与摘要。 |
| 上游可直接获取的小文件，例如脚本、配置、密钥、许可证 | 使用确切上游版本，将文件放入项目。工作区中来源已核实的同版文件可直接复用。 |
| 上游可直接获取的大文件，例如 WAR、JAR、发行包、工具链或源码归档 | 在 Dockerfile 中用 curl/wget 下载。即使 BCLA 终版从本地 COPY，也必须改成镜像构建时下载，保留校验与安装语义。 |
| 第三方 LoongArch Release 或公开发布的架构无关产物 | 有稳定、精确版本且无需本地凭据的下载地址时，按大文件下载规则处理。 |
| 用户提供的前端资源、私有或本地 CI 输出，没有上述稳定下载地址 | 将实际验收的产物放入项目，记录来源与本地摘要，不重新引入原生生成链。 |
| Dockerfile 内部阶段原本直接构建的产物 | 保留该阶段及阶段间复制，不额外拆成宿主机原生构建前置步骤。 |

对目录形式的原生产物，可以采用项目内归档，但必须保留安装所需的路径、权限和链接，并由 Dockerfile 恢复。需要在 Dockerfile 中下载源码再编译的，保留原有构建过程和源码补丁。

## 上游小文件的补丁

需要适配的脚本或配置同时保留精确的上游原始文件与补丁。Makefile 根据两者生成 Dockerfile 实际使用的文件，每次重新生成都从原始文件开始，不会反复原地打补丁。

补丁规则跟踪真实输入、失败即停止、成功后才替换输出；所有消费这些文件的镜像目标都依赖准备步骤。源码在 Dockerfile 内下载后才应用的源码补丁，则仍在相应构建阶段应用。

## 多个最终镜像

全部最终镜像分别提供 `Dockerfile.<目标>`，由同一个 Makefile 编排：

- `make` 或 `make image` 构建所有最终镜像。
- `make push` 推送所有对应的版本标签。
- `make push LATEST=true` 另外为每个目标打上并推送其各自的 latest 标签。

各目标的镜像名必须明确且不冲突，特别是多个 latest 标签不能互相覆盖。普通 Dockerfile 内部构建阶段不算单独交付的最终镜像。

## 中间镜像子项目

只有同时满足“上游明确将其作为独立中间镜像使用”和“BCLA 本次确实构建了它”，才为其创建子目录。该目录内部同样是扁平项目，使用自己的 Makefile 构建和推送，也适用小文件、原生产物、补丁及多镜像规则。

外层 Makefile 不递归构建或推送这个子项目。外层 Dockerfile 使用与子项目输出一致的镜像标签，README 说明先构建中间镜像、再构建最终镜像的顺序。仅拉取的基础镜像、任务辅助容器和内部 builder stage 不会被误拆成子项目。

## Makefile 模板与验证

`assets/Makefile` 保存了用户指定的原始模板，包括 `REGISTRY`、`ORGANIZATION`、`REPOSITORY`、`TAG`、`LATEST`，http/https 代理参数，以及默认构建和显式推送的行为。生成时填写实际镜像身份，仅按需要扩展补丁准备、多个最终镜像和已验证的构建参数，不写入环境中的代理地址。

`references/makefile-patterns.md` 提供补丁规则、多最终镜像和独立中间镜像的实现示例。

默认验证包括本地依赖完整性、补丁输出与终版一致性、镜像标签映射，以及 `make -n` 的构建/推送命令检查。生成项目本身不触发实际镜像构建或推送；原任务已构建成功与新项目实际测试情况会分别说明。用户另行要求执行构建时，才对导出的上下文做相应实测。

导出同时保留实际成功命令中的平台、目标阶段、构建参数和基础镜像覆盖，而非只照抄 Dockerfile 默认值。文件整理、只读证据检查和静态验证可以在宿主机执行，不修改原任务状态、工作区或知识库。默认不重建镜像，不发布产物。

生成项目 README 记录任务 ID、证据 revision、所需工具和验证程度。存在独立中间镜像子项目时，需按说明先构建子项目；捆绑原生产物意味着可重建镜像，不代表所有依赖可从源码重建。
