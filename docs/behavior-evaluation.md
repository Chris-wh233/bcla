# 模型行为验收

本文件是人工/独立模型验收用例，不是 Controller 的规则表。单元测试只证明记录和工具的机械行为；下面的模型判断需要另外观察，不能用匹配 Skill 文本的测试冒充。

使用临时任务与独立工作区，提供原始需求、日志、文件和可查询来源，不预先告诉被测模型期望的技术路线。不得拿用户现有任务作破坏性测试。离线演练必须注明不能替代真实构建。

| 场景 | 观察点 |
| --- | --- |
| 官方 Dockerfile 需要缺失的项目分发包 | 是否先读取 fix-pkg-miss，按指定来源顺序查找，不默认从源码生成 |
| KB 无配方，官方 Dockerfile 仅下载 amd64 包 | 是否区分“无配方”和“无 LoongArch 成品”，先查询实际资源，不直接添加源码构建阶段 |
| KB 配方从源码构建，但当前任务未检查现成资源 | 是否先完成获取决策；可用成品能否替换生成步骤而不抛弃整套打包方案 |
| 同版本 loong64 归档，任务要求 Alpine | 是否验证 ABI/内容和实际消费，不凭文件名接受，也不凭 Alpine 要求直接拒绝 |
| 本次任务已完整查询并选择源码路线，随后出现项目宏定义问题 | 是否直接交 building-first 修复，不重复整个资源搜索 |
| 用户明确指定带补丁源码构建主程序，另缺第三方库 | 主程序是否记录源码约束，第三方库是否仍走资源优先 |
| 原本简单的前端生成遇到新的原生模块 | 是否读取组件来源/CI、重新评估父产物路线；既不一律强行原生，也不凭“前端”直接要求 x86 |
| 已确认无现成产物、输出架构无关，原生需大量适配，有更简单外部生成方案 | 是否直接保存等待合同、脱离原生生成依赖，而不是继续修复其生成器依赖 |
| 同一库供两个不同目标使用 | 是否仅在版本/ABI/选项一致时共享；库自测成功是否被错误当成两个消费者都成功 |
| 相似依赖名但 ABI/版本不兼容 | 是否分别记录版本和消费者，不混用产物 |
| 用户只说“产物好了”，或提供不存在/版本不符的路径 | 是否保持等待并指出缺失信息，不清空等待继续构建 |
| 提供真实且符合合同的产物 | 是否记录实际检查证据并回到原消费者验证 |
| 模型漏记一个失败结果，之后上下文压缩 | 新工具响应是否持续显示未整理结果；是否读取现状，不盲目重启长命令 |
| 切换路线时另一条命令仍在运行 | 命令记录及任务版本是否保留；是否检查真实进程而非认为修改状态就已终止 |
| 暂时替换生成器后产物通过验证，再恢复源文件 | 是否提前保存精确补丁/config和执行证据；经验是否仍能表达真实生成流程 |
| KB 不可用，或存储不可用 | 前者可回退正常分析，后者报告记录失败并停止当前构建活动，不改变技术判断 |
| 同版本存在 Debian 和 Alpine 经验，用户明确要求 Alpine | 是否先过滤最终运行环境再比较版本；Debian 辅助容器是否被误当成目标约束 |
| 同版本多个家族，无显式基础镜像要求 | 是否参考官方变体与兼容性；同等候选是否按路径稳定选择，并记录理由 |
| Dockerfile ARG 默认 Debian，成功命令覆盖为 Alpine，或 final FROM 指向内部阶段 | 是否追踪实际参数和阶段继承，以最终运行环境命名经验，而不是照抄默认值或 builder |
| 成功任务同时包含 Debian 与 Alpine 最终镜像 | 是否分别生成完整经验并分配对应目标/证据；依赖是否留在各自变体内 |
| 同版本同家族但不同 Debian 标签导致构建方案冲突 | 是否保留旧经验并报告冲突，而非覆盖或偷偷增加标签目录 |
| 新索引损坏但版本/家族经验文件仍完整 | 是否扫描该项目的经验元数据、跳过依赖并正常选择，无法使用时回退分析 |

验收记录应包含：输入、工具实际调用、关键决策前后记录、模型决定、引用证据、未验证项。不能仅凭最终产物成功就认定过程合规，也不能把一次合理的原生构建尝试认定为违例。

先用固定用例验证不丢上下文，再使用未见过的项目/依赖组合验证泛化。若失误来自规则歧义，修正文档职责；若来自丢失执行事实，修复记录接口。不为单个包名称增加调度分支或强制流程状态。
